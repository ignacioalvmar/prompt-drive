# Vehicles plan — Truck and self-driving Shuttle

Status: **Phase 1 (Truck) and Phase 2 (Shuttle) implemented.**

## 0. Why Bike and Coach show no vehicle

The vehicle menu (`ze = ["Roadster", "Bike", "Coach"]` in
`src-extracted/deobfuscated.js`) offers three vehicles, but only the Roadster's
meshes ship in `static/media/`. The engine definitions still point at upstream
assets that were never checked in:

| Def | Body OBJ | Wheel OBJ | In repo? |
| --- | --- | --- | --- |
| `Ne.Roadster` | `roadster-07-int.9a99909d.obj` | `roadster_wheel_02.bbc40837.obj` | yes |
| `Ne.Bike` | `mono_2.a6225cf4.obj` | `mono_wheel.0c7cdca8.obj` | **no** |
| `Ne.Bus` ("Coach") | `bus-02.07c5f9f2.obj` | `bus-wheel.32095e6e.obj` | **no** |
| `Ne.Debug` / `Ne.Rover` | `debug_body.193b9327.obj` | `debug_wheel.291c4dc1.obj` | **no** |

`initVehicle` purges the old geometry, the OBJ loads 404, and the wheel-load
callback (which re-enables the update loop) never fires, so you get an empty
rig. The traffic subsystem already works around the missing Coach assets
(`TrafficAssets.isFailed('Coach')`).

**Decision:** stop offering vehicles we cannot render. The menu becomes
`Roadster, Truck` (Phase 1) and then `Roadster, Truck, Shuttle` (Phase 2). The
`Ne.Bike` / `Ne.Bus` definitions stay in the engine source, unreferenced, so
they can be put back with a one-line change if the upstream OBJs are recovered.
A stored `config-vehicle-type` that names a vehicle no longer offered (e.g. an
old `"Coach"`) falls back to the Roadster instead of loading an empty rig.

## 1. How a vehicle is put together (engine contract)

A vehicle is one entry in `Ne` (the def table) plus an entry in `je` (type name
→ def) and `ze` (menu order). `initVehicle(def)` then:

1. `Ae.setModel(def)` copies `metrics`, `wheels`, `cameras`, `bike` onto the ego
   controller (`Ae`) and positions the headlight spotlights from
   `metrics.headlightPos`.
2. Sets the shared `_d.map` material's texture from `def.map`.
3. Loads `bodyObj` with `OBJLoader`. **Each mesh's material is chosen from its
   object name**: `name.split("_")[1]` is looked up in `_d` (`map`, `body`,
   `window`, `black`, `grey`, `metal`, `tire`, `headlight`, `rearlight`,
   `redlight`, `shadow`, …); unknown keys get `_d.default` (the grey interior
   Phong). `shadow` meshes cast shadows but write no colour.
4. Loads `wheelObj` once and clones it into four wheels at
   `(±width/2, radius, length)` (front) and `(±width/2, radius, 0)` (rear) —
   **the origin is the rear axle**, +Z forward, +Y up. Body OBJs are authored
   with +X forward (rotated −π/2 on load).
5. Optionally loads `steerObj` (steering wheel) and `dashObj` (binnacle) at
   `metrics.steeringPos`, mirrored by the driver-side setting.

First-party subsystems that depend on the vehicle:

| Subsystem | Dependency | Impact for new vehicles |
| --- | --- | --- |
| Instrument cluster | finds the `z_dashboard_Cube.009` mesh (from `dashboard.obj`) | Works for free if the new vehicle reuses `dashObj` |
| Center console | finds `z_interior_Cube.008` and mounts at a hard-coded Roadster point `(x 1.9242, y 0.8672)` | Needs a per-vehicle `metrics.consoleMount` |
| Traffic | ego box = `wheels.length + 1.2`, computed once at attach | Needs real body dims (`metrics.dims`) and refresh on vehicle change |
| Nav app | ego box on the map, same approximation | Use `metrics.dims` |
| Integration API | `vehicle.type` enum `['Roadster','Coach']` | Update enum, docs |
| Autopilot | pure pursuit from rear axle: `steer = atan(wheels.length / R)`; clamps to `metrics.maxSteer`; speed targets from `metrics.topSpeed`, braking from `metrics.brake` | Geometry adapts to wheelbase automatically; tune metrics |

## 2. Shared design decisions

- **Procedural, versioned meshes.** There is no 3D tooling in the repo, so new
  vehicle OBJs are generated by a Node script (`scripts/gen-vehicles.js`,
  `npm run gen:vehicles`) from readable box/panel descriptions. The generated
  OBJs are committed under `static/media/` like the other assets.
- **Same look as the Roadster.** Painted panels use the `map` material and are
  UV-mapped onto regions of the Roadster atlas (`roadster-07b_map.jpg`): its
  flat white body paint, its blue-grey glass panels, its black trim and — on
  the truck's lower cab front — the Roadster's nose fascia (headlight graphics,
  grille). Lamps use the same emissive `headlight` / `rearlight` / `redlight`
  materials, so brake lights and night driving behave identically.
- **Reuse the Roadster's binnacle and steering wheel** (`dashObj`, `steerObj`)
  positioned at the new `steeringPos`. This keeps the instrument cluster, the
  steering-wheel animation and the "Interior: Show wheel" toggle working with
  no subsystem changes.
- **Cab interiors are double-skinned.** Opaque cab panels emit an outward face
  (`map`) and an inward face (`interior`) so the first-person camera sees
  walls, pillars and a dash; glass is outward-only, so from inside you look
  straight through it.
- **Body dims as data.** Each def gets `metrics.dims = { front, rear, width }`
  (metres from the rear axle). Traffic collision boxes, gap keeping and the nav
  map use it when present, falling back to the old wheelbase approximation.

## 3. Phase 1 — Truck (implemented)

A cab-over two-axle box truck (≈ 7.5 t delivery class).

| | Roadster | Truck |
| --- | --- | --- |
| Wheelbase / track | 2.75 m / 1.36 m | **4.20 m / 2.00 m** |
| Wheel radius | 0.34 m | **0.50 m** |
| Overall length / width / height | ~4.1 / 1.6 / 1.2 m | **~7.7 / 2.5 / 3.6 m** |
| Top speed | 45 m/s | **25 m/s (90 km/h)** |
| Max steer | 0.68 rad | **0.60 rad** |
| Accel / brake | 9 / 8 | **7 / 5** (≥ 7 needed to keep climbing the engine's ~19 % grades) |
| Driver eye height | ~1.1 m | **~2.4 m** |

**Exterior** — white cab with raked windscreen, side windows, roof air
deflector, black bumper, Roadster-style nose fascia, emissive headlights, side
mirrors; white cargo box with black seams, tail/brake lights; black chassis
rails; procedurally generated truck wheels (black tyre, metal rim, lug pattern
so rotation is visible).

**In-cabin view** — `FirstPerson` camera at `(±0.60, 2.38, 4.30)`: the driver
sits just behind the front axle, ~2.4 m above the road, looking down through a tall
windscreen with no bonnet in view. The steering wheel is tilted flatter
(`steeringAngle 0.6`) like a truck wheel. Seat height / adjustment settings
still apply on top. The center console mounts on the truck dash via
`metrics.consoleMount`.

**Cameras** — `Chase` and `ChaseFar` pulled back and raised for the larger
body, `FirstPerson`, and a front-bumper `Hood` view.

**Dynamics / autopilot** — the pure-pursuit autopilot already scales with the
wheelbase. The truck's lower `maxSteer`, `steerSpeed`, `accel`, `brake` and
`topSpeed` make it turn wider, accelerate slower and brake earlier; the
autopilot's corner speed target (`topSpeed · 0.6–0.8`) and brake threshold
(`metrics.brake`) follow from those numbers. Verification checklist:

- [ ] Truck appears in the vehicle menu and renders (body, 4 wheels, lights).
- [ ] Manual driving: accelerates, brakes, steers; wheels rotate and steer.
- [ ] Autopilot completes tight bends without leaving the road or oscillating.
- [ ] Autopilot respects the lane offset on multi-lane roads.
- [ ] First-person view is elevated, wheel + cluster + console visible.
- [ ] Driver side setting mirrors seat, wheel and cluster.
- [ ] Switching Roadster ↔ Truck live works; traffic ego box updates.
- [ ] Headlights at night; brake lights on braking.
- [ ] `PromptDrive.config.set({ 'vehicle.type': 'Truck' })` works via API.

Follow-ups (not in Phase 1): a tandem rear axle (needs `initWheels` to accept
N axles — engine patch), truck in the traffic mix, a truck engine sound.

## 4. Phase 2 — Self-driving Shuttle (implemented)

A 6–12 seat autonomous people-mover (EasyMile / Navya / Holon class): a
symmetric "bread-box" body, large glass area, no driver's cab.

| | Truck | Shuttle |
| --- | --- | --- |
| Wheelbase / track / wheel radius | 4.2 / 2.0 / 0.5 m | **2.9 / 1.75 / 0.38 m** |
| Length / width / height | ~7.7 / 2.5 / 3.6 m | **4.8 / 2.1 / 2.55 m** |
| Top speed | 25 m/s | **12 m/s**; autopilot cruises 7 m/s, **5 m/s in bends** (`bendSpeed`) |
| Accel / jerk / brake | 7 / 16 / 5 | **6 / 6 / 3** (gentle ramps for standing passengers; 6 still climbs the steep grades) |
| Steering | wheel + binnacle | **none** (`driverless: true`) |

**Exterior** (`shuttle-01.obj`, generated) — chamfered corners with
wrap-around glass, a window band of glass panes between white pillars, black
skirt, wheel-arch cut-outs with black liners, sliding-door seams on the +Z
side, the Roadster nose fascia on the lower front, emissive light bars front
and rear (tail + brake). Same atlas and lamp materials as the other vehicles.

**Interior** — inward-facing shell, floor and ceiling; wheel-arch housings;
a forward-facing rear bench and a rear-facing front bench (`grey` material);
four vertical poles and two ceiling rails (`metal`).

**Passenger seats** — `metrics.seats` lists camera positions, chosen by the
new `passengerSeat` VehicleConfig field (settings panel "Shuttle: Passenger
seat", API `vehicle.passengerSeat`, live or static):

| # | Seat | Position (x, y, z) | Facing |
| --- | --- | --- | --- |
| 0 | Rear bench, window | (0.6, 1.6, −0.6) | forward |
| 1 | Rear bench, centre | (0, 1.6, −0.6) | forward |
| 2 | Front bench, facing back | (0.6, 1.6, 3.5) | backward (yaw π) |
| 3 | Standing, by the door | (−0.55, 2.05, 1.45) | forward |

The `updateFirstPerson` patch places the camera at the seat (not mirrored by
the driver-side setting) and adds the seat yaw to the view heading; seat
height / adjustment still apply.

**Passenger info display** — the instrument cluster gains an `info` anchor
mode: when the vehicle publishes `metrics.infoDisplay` (body-OBJ placement,
1.2 × 0.37 m under the front header) it mounts there and draws a passenger
layout (`src/cluster/passenger.js`): line name, next stop with distance bar
and ETA, the stop after, speed, clock, and the driving mode —
**AUTOMATED DRIVING** or **SAFETY OPERATOR IN CONTROL**. Stops are simulated
(a 7-stop loop, 700 m apart, advanced by integrating speed); the shuttle does
not halt at them yet. `consoleMount: null` hides the center console.

**Driverless behaviour** — the autopilot switches on whenever the shuttle
finishes loading. Turning it off (F / API) hands control to a "safety
operator": normal manual driving, reflected on the info display.

**Autopilot bend speed** — the engine's bend target was a fixed 15 m/s blended
toward `topSpeed · 0.6–0.8` on straights. For a 12 m/s vehicle that made the
target *higher* in bends than on straights. `metrics.bendSpeed` (default 15,
so Roadster and Truck are unchanged) replaces the constant.

Verification (browser, sim-time clock):

- [x] Renders in chase view; exterior 3/4 view checked.
- [x] Autopilot: 227 m winding road, 0 resets, 0 off-road, lane offset
      1.34–1.55 m, 6.6–10.2 m/s.
- [x] All four seats, including rear-facing; live switch via
      `PromptDrive.dynamic.set({ 'vehicle.passengerSeat': n })`.
- [x] Info display mounted and legible from the rear bench; console hidden.
- [x] Roadster ↔ Shuttle swap: autopilot turns on for the shuttle, cluster
      and console return to driver mode for the Roadster.
- [ ] Night lighting of the light bars by eye; menu selection by click.

Follow-ups: real stops (decelerate, dwell with door "open", depart) driven by
the same route model; a second info display facing the front bench; hide the
steering-wheel setting for driverless vehicles; comfort KPIs (jerk, lateral
acceleration) surfaced per vehicle in `src/metrics`.
